# School Site — Project Memory & Guidelines

School website built with **Next.js 16 + Payload CMS 3**. Keep the structure
clean and reusable.

See @docs/PROJECT_CONTEXT.md for full background.
See @README.md for setup and run commands.

---

## Stack (do not swap without asking)
- Next.js 16 (App Router), React 19, TypeScript 5
- Payload CMS 3 (embedded — admin lives at `/admin`, same app)
- PostgreSQL via `@payloadcms/db-postgres`
- Lexical rich text (`@payloadcms/richtext-lexical`)
- Tailwind CSS v4 + shadcn/ui for the public UI (add when styling; not yet installed)

---

## General Principles

- Prefer editing existing files over creating new ones.
- No comments unless the WHY is non-obvious.
- No speculative abstractions — solve what is in front of you.
- No half-finished implementations.
- Always validate at system boundaries (form input, CMS webhooks, API responses); trust internal types otherwise.

## Project Layout

- `src/payload.config.ts` — single source of truth (collections, globals, db)
- `src/collections/` — one file per collection (Users, Media, Pages, Posts, Galleries, Videos, Faculty, Students)
- `src/globals/` — SiteSettings, Header, Footer
- `src/blocks/` — reusable Page layout blocks (Hero, RichTextBlock, ImageText, Timeline)
- `src/access/index.ts` — shared access-control functions; ALWAYS reuse these, don't inline access logic
- `src/app/(frontend)/` — public site (Server Components reading via Payload Local API)
- `src/app/(payload)/` — Payload admin UI (generated by create-payload-app; do not hand-edit)

```
src/
  app/
    (frontend)/           # Public-facing site route group
    (payload)/            # Payload CMS admin route group (auto-generated)
  collections/            # Payload collection configs
  globals/                # Payload global configs
  blocks/                 # Reusable page layout block renderers
  access/                 # Shared access-control helpers
  components/
    ui/                   # Generic, reusable primitives
    layout/               # Page-level layout parts (Header, Footer, Nav)
  lib/                    # Shared utilities and helpers
  types/                  # Shared TypeScript types
  styles/
    globals.css           # Tailwind base layer + CSS custom properties
```

## Conventions

- Read/write data with the **Local API** (`getPayload({ config })` then `payload.find/findGlobal`) in Server Components — no fetch to `/api`.
- Public pages use ISR: `export const revalidate = 60`. The student portal is `force-dynamic`.
- Every collection sets explicit `access` using helpers from `src/access`. Never leave access undefined.
- Content that the public reads (posts, pages) uses draft versions + `adminsOrPublished` read access.
- Run `pnpm generate:types` after changing any collection/global, then use the generated types.
- Slugs are lowercase-kebab, stored in a `slug` field, unique + indexed.

---

## IMPORTANT — Security Rules

- The `students` collection holds PII. NEVER make it publicly readable. Read access is
  `ownStudentRecordOrAdmin` only. Do not add public endpoints that expose student data.
- The student auth idea (Admission No + Date of Birth) is WEAK. Do NOT ship DOB as a sole
  credential. For production, keep Admission No as the identifier but add a
  one-time code (email/SMS/WhatsApp) + rate limiting + lockout before exposing records.
- NEVER commit `.env`. Secrets only via environment variables.
- Route handlers (`app/api/*/route.ts`) must validate and sanitize all input before touching the database.
- Never construct SQL with string interpolation — use parameterized queries or the Payload query API.

---

## When Building a Feature

1. Add/adjust the collection or global first; regenerate types.
2. Verify it in the running `/admin` panel.
3. Build the matching public page under `src/app/(frontend)/`.
4. Keep one concern per change; small commits.

## HTML & Semantic HTML

### Best Practices
- Use the correct semantic element for content: `<nav>`, `<main>`, `<article>`, `<section>`, `<aside>`, `<header>`, `<footer>`, `<figure>`, `<figcaption>`, `<time>`, `<address>`.
- One `<h1>` per page; heading levels must not skip (h1 → h2 → h3).
- Every `<img>` must have a descriptive `alt`. Decorative images use `alt=""`.
- Interactive elements (`<button>`, `<a>`) must be keyboard-reachable and have visible focus styles.
- Use `<button>` for actions, `<a href>` for navigation — never the reverse.
- Forms: always pair `<label>` with its control via `for`/`id` or wrap the control inside the label.
- Use `<table>` only for tabular data; add `<caption>`, `scope` on `<th>`, and `<thead>`/`<tbody>`.
- Prefer native HTML elements over ARIA when a native element exists.

### Accessibility (Color Blindness & Low Vision)
- Never rely on color alone to convey meaning — pair with icons, patterns, or text labels.
- Minimum contrast ratios: 4.5:1 for normal text, 3:1 for large text (WCAG AA). Aim for AAA (7:1) where possible.
- Test with a color-blindness simulator (e.g., Stark, Colour Contrast Analyser).
- Avoid red/green as the only differentiators; add shape or label cues.

## CSS

### Best Practices
- Use CSS custom properties (`--color-primary`) for design tokens; define them on `:root`.
- Follow a consistent naming convention: BEM for handwritten CSS, or rely on Tailwind utilities.
- Avoid magic numbers; derive spacing from a scale.
- Use `clamp()` for fluid typography; avoid fixed `px` for font sizes.
- Prefer logical properties (`margin-inline`, `padding-block`) for RTL compatibility.
- Do not use `!important` except to override third-party styles — document why when you do.
- Use `prefers-reduced-motion` media query to disable or reduce animations.
- Use `prefers-color-scheme` to support dark mode at the OS level.

---

## Tailwind CSS v4

### Best Practices
- Use semantic utility groupings in JSX — group layout, then spacing, then typography, then color, then state.
- Extend the theme in `tailwind.config.ts` for brand colors and font families; do not hardcode arbitrary values in class lists.
- Use `@apply` sparingly — only in a `globals.css` base layer for recurring multi-utility patterns (e.g., prose, card).
- Responsive prefixes: `sm:`, `md:`, `lg:`, `xl:` — mobile-first, never desktop-first.
- Use `focus-visible:` instead of `focus:` for keyboard focus styles to avoid outline on mouse click.
- Enable `aria-*` and `data-*` variants to drive state styling from markup rather than JS class toggling.
- Use `text-balance` and `text-pretty` for headings and prose.

### Accessibility with Tailwind
- Always include a visible focus ring: `focus-visible:ring-2 focus-visible:ring-offset-2 focus-visible:ring-primary`.
- Do not remove outlines without replacing them: `outline-none` is only acceptable alongside a custom ring.
- Use `sr-only` for text that should be read by screen readers but not visible.

## Next.js (App Router)

### Best Practices
- Default to **React Server Components (RSC)**; add `"use client"` only when the component needs browser APIs or interactivity.
- Co-locate loading states with `loading.tsx` and error boundaries with `error.tsx` in each route segment.
- Use `generateMetadata` per page for SEO; never rely on a single root-level meta tag.
- Use `next/image` for all images — always provide `width`, `height` or `fill` with a sized parent, and a meaningful `alt`.
- Use `next/font` to self-host fonts; remove Google Fonts CDN calls.
- Use `next/link` for all internal navigation; never use `<a>` for internal links.
- Prefer `fetch` with `cache` options over third-party data-fetching in Server Components.
- Keep secrets in `.env.local`; never import `process.env` in Client Components — expose only via `NEXT_PUBLIC_` prefix when needed.
- Use `unstable_cache` or `revalidatePath`/`revalidateTag` for ISR; document the revalidation strategy at the top of the file.

### Performance
- Use `Suspense` boundaries to stream slow data; keep the shell lightweight.
- Avoid large Client Component trees; lift data fetching to Server Components.
- Use dynamic imports (`next/dynamic`) for heavy client-only libraries (e.g., rich text editors).

## React 19

### Best Practices
- Prefer function components; no class components.
- Name components with PascalCase; name files to match the component exactly.
- Co-locate component, types, and tests in the same folder when the component is complex.
- Use the `use` hook and React Server Actions for data mutations instead of standalone API routes where possible.
- Keep components small and single-responsibility; extract sub-components when JSX exceeds ~80 lines.
- Avoid prop drilling deeper than two levels — use React Context or a state library.
- Do not put side effects directly in the render body; use `useEffect` with explicit dependency arrays.
- Memoize selectively (`useMemo`, `useCallback`) — only when profiling shows a measured benefit.
- Use `key` props on lists with stable, unique IDs — never array indices for dynamic lists.

### Accessibility in React
- Dynamic content updates must announce themselves: use `aria-live="polite"` regions or move focus deliberately.
- Modal dialogs must trap focus and restore it on close.
- Custom interactive components (dropdowns, tabs, accordions) must implement the correct ARIA pattern (WAI-ARIA Authoring Practices).

## Payload CMS 3

### Best Practices
- Collection and global configs live in `src/collections/` and `src/globals/` (this project's layout).
- Use Payload's built-in access control functions from `src/access/` — never bypass with raw DB queries for permission-sensitive data.
- Use `hooks` (beforeChange, afterChange) for side effects (cache invalidation, email triggers); keep them focused and fast.
- Enable `versions` on content collections for editorial draft/publish workflows.
- Use `richText` fields with a consistent lexical config; do not mix lexical and slate.
- Validate field input with Payload's `validate` property; do not rely solely on database constraints.
- Keep media uploads in a dedicated `Media` collection with `focalPoint` enabled.
- Use `relationship` fields with `hasMany` and `filterOptions` to avoid orphaned references.
- Seed scripts go in `src/seed/`; never run seeding in production without a guard check.

## TypeScript 5

### Best Practices
- Enable strict mode in `tsconfig.json`: `"strict": true`.
- Prefer `type` aliases for unions and intersections; use `interface` for object shapes that may be extended.
- Never use `any` — use `unknown` and narrow with type guards.
- Use Zod or Payload's generated types for runtime validation at API boundaries.
- Export types from a dedicated `types.ts` alongside the module that owns them.
- Use `satisfies` operator to validate literals against a type without widening.
- Avoid type assertions (`as`) except when interfacing with untyped third-party code — document why.
- Use `const` assertions (`as const`) for fixed config objects and lookup maps.
- Payload CMS auto-generates TypeScript types — import from `@/payload-types` rather than duplicating shapes.

---

## JSON

### Best Practices
- Use JSON for static config, feature flags, and data interchange — not for logic.
- Always validate JSON from external sources against a schema (Zod, JSON Schema) before use.
- Prefer `.json` extension with explicit `import type` assertions in TypeScript when importing static JSON.
- Keep JSON keys camelCase to match TypeScript conventions.
- Do not store secrets or credentials in JSON files committed to the repository.

---

## PostgreSQL (via Payload CMS)

### Best Practices
- Let Payload manage migrations via `payload migrate`; do not write raw DDL unless absolutely necessary.
- Use Payload's `db.transaction()` for multi-step writes that must be atomic.
- Add database indexes on fields used in filters and sorts in collection configs (`index: true`).
- Use `drizzle-orm` (Payload v3's default adapter) type-safe query builders for any custom queries outside Payload's API.
- Back up the database before running migrations in production.
- Use connection pooling (default in Payload's drizzle adapter) — do not create ad-hoc connections.
- Store the `DATABASE_URI` in `.env.local`; never hardcode credentials.

---

## Accessibility (Global)

- Target **WCAG 2.2 Level AA** as the minimum.
- Test with keyboard-only navigation for every interactive feature.
- Test with a screen reader (VoiceOver on macOS, NVDA on Windows) before shipping.
- Use landmark regions on every page: `<header>`, `<nav>`, `<main>`, `<footer>`.
- Skip-navigation link must be the first focusable element on every page.
- All form errors must be associated with their field via `aria-describedby`.
- Color contrast must pass for both light and dark modes.

---

## Mobile-First Design

- Write Tailwind classes mobile-first; add `sm:` / `md:` / `lg:` overrides for larger viewports.
- Touch targets must be at least 44×44 px.
- Avoid hover-only interactions — pair with `focus` and `active` states.
- Test on real devices or browser DevTools at 375 px (iPhone SE) and 390 px (iPhone 14) widths.
- Use `next/image` responsive sizes with `sizes` prop to serve appropriately sized images to mobile.
